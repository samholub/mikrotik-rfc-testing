# RouterOS native traffic-testing capabilities vs RFC 2544 / ITU-T Y.1564

Scope: MikroTik first-party features, docs, MUM material and product-page methodology only. Researched 2026-09-30.
Source-quality key: **[DOC]** = MikroTik official documentation / product page / MUM slide by MikroTik; **[FORUM]** = community anecdote; **[STD]** = standards text; **[INF]** = my inference, not stated anywhere.

Doc-site note: help.mikrotik.com (Confluence) and a newer manual.mikrotik.com both carry the RouterOS manual; a search snippet described help.mikrotik.com as frozen with manual.mikrotik.com as the new site (not verified on a MikroTik page). The old wiki.mikrotik.com now 307-redirects to help.mikrotik.com; wiki pages quoted below were read from the Internet Archive copy (Jan 2023 cache), i.e. they describe ROS 6-era behaviour.

## 1. /tool traffic-generator: parameters, measurement semantics, limits, fit for RFC 2544 / Y.1564

### Takeaway
Traffic Generator is the only native RouterOS tool that produces RFC 2544-shaped measurements (per-stream TX/RX/lost counts, latency min/avg/max, jitter, out-of-order, latency histogram, exact L2 frame sizes), and unlike btest it does not need a MikroTik at the far end. But it computes loss as TX minus RX on the *same* router, so its packets must come back to the generator: on a circuit that means a routed loop through the far end (round-trip, not per-direction, results), it is CPU-generated (no hardware assist documented), and on factory ROS 7.17+ devices it is disabled by device-mode and needs physical access to enable. It has no built-in binary search, CIR/EIR stepping or pass/fail - those would have to be scripted.

### Cited Findings
**What it is / what it measures**
- [DOC] "Traffic Generator is a tool that allows evaluating the performance of DUT (Device Under Test) or SUT (System Under Test)." It "can generate and send RAW packets over specific ports" and "collects latency and jitter values, TX/RX rates, counts lost packets, and detects Out-of-Order (OOO) packets." — [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator)
- [DOC] "Traffic Generator can be used similar to bandwidth test tool as well as generate packets that will be routed back to packet generator for advanced status collection." — [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator); same wording in the [MUM EU17 study case (J. M. Roman, FiberCLI)](https://mum.mikrotik.com/presentations/EU17/presentation_4081_1490963921.pdf)
- [DOC] Introduced in RouterOS v6: "RouterOS version 6 introduces a new tool - 'traffic generator', which allows performing performance testing without expensive testing hardware." — [wiki Manual:Performance Testing with Traffic Generator](https://wiki.mikrotik.com/wiki/Manual:Performance_Testing_with_Traffic_Generator) (read via archive copy)

**Menus and parameters** (all from [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator) unless noted) [DOC]
- `/tool traffic-generator`: `latency-distribution-max` (default 100us), `measure-out-of-order` (yes|no), `stats-samples-to-keep` (default 100), `test-id` (0-255); read-only `running`, `latency-distribution-samples`, `latency-distribution-measure-interval`. Commands: `quick`, `start` (test-id), `stop`, `inject`, `inject-pcap`.
- `quick` accepts: duration, entries-to-show, freeze-frame-interval, id, interface, mbps, measure-out-of-order, packet-count, packet-size, port, pps, stream, test-id, tx-template. Wiki: "tx-template - packet templates to generate traffic (max 16 templates)"; "Parameters specified when running quick command overrides configured values." — [wiki Manual:Tools/Traffic Generator](https://wiki.mikrotik.com/wiki/Manual:Tools/Traffic_Generator) (archive copy)
- `packet-template`: `header-stack` (mac 14 B, vlan 4 B, ip 20 B, udp 8 B, raw; max 2 IP headers, 1 UDP header), `ip-src/ip-dst`, `mac-src/mac-dst`, `udp-src-port/udp-dst-port`, `ip-ttl`, `ip-protocol`, `ip-dscp` (DS byte incl. ECN), `ip-frag-off`, `ip-id` - list-type fields take up to 16 values; `data` (incrementing|random|specific-byte|uninitialized), `data-byte`, `interface` or `port`, `ip-gateway` ("used when sender/receiver identical; helps determine destination MAC"), `compute-checksum-from-offset`, `vlan-id/vlan-priority/vlan-protocol`, `raw-header`. Unspecified fields are "assumed" (e.g. next-hop MAC via ARP); "Assumed values are not automatically updated. New values are assumed after template edit."
- `port`: `name`, `interface`, `disabled`.
- `stream`: `num` (0-15, i.e. max 16 streams), `mbps`, `pps`, `packet-size` (1-65535 or a range for random sizes), `port`, `tx-template`, `disabled`. Wiki: "each stream has unique id value. This value identifies stream packets, otherwise traffic generator will not work." — [wiki Manual:Tools/Traffic Generator](https://wiki.mikrotik.com/wiki/Manual:Tools/Traffic_Generator)
- `mbps`: "Value in Megabits per second that the stream will try to generate." `pps`: "Packets per second that the stream will try to generate." — [manual.mikrotik.com Traffic Generator](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/traffic-generator/)
- No parameter named `inject-pps` exists in any version of the doc I read; the rate controls are `mbps`/`pps` per stream (and on `quick`). — [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator)
- Wiki note: "speed in quick mode is specified per stream, so if you have two streams per port, you need to send 1/2 of traffic per stream" — [wiki Performance Testing](https://wiki.mikrotik.com/wiki/Manual:Performance_Testing_with_Traffic_Generator)

**Frame size semantics (maps cleanly onto RFC 2544 sizes)**
- [DOC] "We are specifying 60 byte packet in traffic generator to get a 64 byte packet on ethernet." Their other tests use `packet-size=508` and `packet-size=1514` for 512/1518 B frames, i.e. `packet-size` = L2 frame including the 14 B Ethernet header, excluding the 4 B FCS. — [wiki Performance Testing](https://wiki.mikrotik.com/wiki/Manual:Performance_Testing_with_Traffic_Generator)
- [DOC] The current manual defines packet-size only as "Generated size of the packets in bytes. Can be set as the range for random packet size generation." without naming the layer. — [manual.mikrotik.com Traffic Generator](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/traffic-generator/)

**Statistics**
- [DOC] `stats stream`: SEQ, NUM, TX-PACKET, TX-RATE, RX-PACKET, RX-RATE, LOST-PACKET, LOST-RATE; `stats port`: adds RX-UNK-PACKET/BYTE/RATE (packets not recognised as generator packets); `stats raw`: per port per stream; `stats latency-distribution`: histogram (LATENCY range, COUNT, SHARE, GRAPH), printable per stream or per sequence. "If traffic generator is not running in quick mode then all statistics about the test is stored in this menu." — [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator); [wiki Manual:Tools/Traffic Generator](https://wiki.mikrotik.com/wiki/Manual:Tools/Traffic_Generator)
- [DOC] Loss is computed as TX minus RX on the generator. In the wiki `stats raw` example a stream shows `port0 TX 43 064 / RX 0 / LOST 43 064` and `port1 TX 0 / RX 25 180 / LOST -25 180`, with the per-stream TOT row `TX 43 064 RX 25 180 LOST 17 884`. — [wiki Manual:Tools/Traffic Generator](https://wiki.mikrotik.com/wiki/Manual:Tools/Traffic_Generator)
- [DOC] `quick` output in the official docs shows SEQ, NUM, TX-PACKET, TX-RATE, RX-PACKET, RX-RATE, RX-OOO, LOST-PACKET, LOST-RATE; text after it says "Stats shows throughput of each stream and total throughput of both streams, Out-of-order packet count, Lost rate, latency and jitter." The official Performance Testing examples print an extra trailing latency column (e.g. `16us`, `3.15ms`). — [wiki Manual:Tools/Traffic Generator](https://wiki.mikrotik.com/wiki/Manual:Tools/Traffic_Generator); [wiki Performance Testing](https://wiki.mikrotik.com/wiki/Manual:Performance_Testing_with_Traffic_Generator)
- [FORUM] A user's `quick` output shows columns SEQ, ID, TX-PACKET, TX-RATE, RX-PACKET, RX-RATE, RX-OOO, RX-BAD-CSUM, LOST-PACKET, LOST-RATE, LAT-MIN, LAT-AVG, LAT-MAX, JITTER, and a template with `special-footer=yes`; with nothing coming back, RX was zero. — [forum t=117827](https://forum.mikrotik.com/viewtopic.php?t=117827)
- [DOC-gap] None of help.mikrotik.com, manual.mikrotik.com or the archived wiki mention "special-footer", "timestamp", "signature", LAT-MIN or JITTER; how latency is stamped and how jitter is defined are undocumented. — [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator)

**CPU, multi-core, capture limits**
- [DOC] measure-out-of-order: "Default value is based on CPU type (multi-core CPU default no; single-core CPU default yes). When the property is enabled on the multi-core device, a single stream will utilize only a single CPU core." — [wiki Manual:Tools/Traffic Generator](https://wiki.mikrotik.com/wiki/Manual:Tools/Traffic_Generator)
- [FORUM] CCR1009 on 6.44.3 did not report OOO until `measure-out-of-order=yes`; the same user noted "Unlike the Bandwidth Test it can be used with any other vendor." — [forum: Traffic Generator on multi-core Mikrotiks (2019)](https://forum.mikrotik.com/t/traffic-generator-on-multi-core-mikrotiks/130197)
- [DOC] "In a device, which generates packets, it will not be possible to capture packets generated by the traffic-generator with a sniffer tool, torch, or firewall on the outgoing interface." — [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator)
- [DOC] Generation costs more than forwarding: for a CCR1036 DUT test "we will require 2 other CCR1036 as passing data through is not as intensive as generating traffic and gathering statistical data." — [wiki Performance Testing](https://wiki.mikrotik.com/wiki/Manual:Performance_Testing_with_Traffic_Generator)
- [DOC] Rates in MikroTik's own examples (ROS 6): an RB1100AHx2 generator pushing 6 streams of 64 B frames sent ~1.30-1.50 Mpps total (e.g. `TOT 1 297 032 ... 635.3Mbps`, `1 498 751 ... 735.3Mbps`); 1514 B at 3.9 Gbps TX over 4 ports; the IPsec example sent ~909 Mbps of 1450 B packets. — [wiki Performance Testing](https://wiki.mikrotik.com/wiki/Manual:Performance_Testing_with_Traffic_Generator); [wiki Manual:Tools/Traffic Generator](https://wiki.mikrotik.com/wiki/Manual:Tools/Traffic_Generator)
- [DOC] No hardware offload / switch-chip generation is mentioned anywhere on the Traffic Generator pages. — [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator)

**ROS 7 changes**
- [DOC] Device-mode: `traffic-gen` is disabled by default in all modes (home, basic, advanced, ROSE); `bandwidth-test` is enabled in advanced and ROSE but disabled in home and basic. "Device-mode configuration is factory pre-installed to routers (for devices with MikroTik RouterOS v7.17 or later)." Changing it requires physical access: press a button or cold-reboot within the activation timeout (default 5 min). — [help.mikrotik.com Device-mode](https://help.mikrotik.com/docs/spaces/ROS/pages/93749258/Device-mode); lock command `/system device-mode update traffic-gen=no` quoted in [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator)
- [DOC] inject-pcap accepts PCAPNG from RouterOS 7.21 (the sniffer switched to saving PCAPNG in 7.20). — [manual.mikrotik.com Traffic Generator](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/traffic-generator/); changelog summary via search of [v7.21 stable announcement](https://forum.mikrotik.com/t/v7-21-stable-is-released/267773) and [v7.20 stable announcement](https://forum.mikrotik.com/t/v7-20-stable-is-released/265196)
- [DOC] MikroTik's EU19 MUM slide lists Traffic Generator as: determines transfer rates and packet loss, detects OOO, collects latency and jitter, injects/replays pcap, "Quick" mode, "Full Winbox support (coming soon)", "Doesn't have TCP protocol support", "Scares people". — [MUM EU19 "Understanding throughput"](https://mum.mikrotik.com/presentations/EU19/presentation_6767_1552293932.pdf)
- [FORUM] hEX S on 6.49.10 generating toward a Juniper SSR: traffic initially did not arrive; jitter did not display. No staff reply. — [forum: Traffic generator strange problem (Jan 2025)](https://forum.mikrotik.com/t/traffic-generator-strange-problem/181165)

**Standards requirements it would need to meet** [STD]
- RFC 2544: Ethernet frame sizes "64, 128, 256, 512, 1024, 1280, 1518"; throughput is the highest rate with zero loss, trials "SHOULD be at least 60 seconds"; latency stream "at least 120 seconds", tagged frame after 60 s, "repeated at least 20 times"; frame-loss rate in steps no coarser than 10% of max rate; back-to-back bursts "at least 2 seconds", "repeated at least 50 times". — [RFC 2544](https://www.rfc-editor.org/rfc/rfc2544.txt)
- RFC 6815: RFC 2544 methods "are intended to generate traffic that overloads network device resources"; on production networks this is harmful, the test conditions are not achieved, and frame loss has uncontrolled causes; it points to IPPM metrics and ITU-T Y.1564 for production use. — [RFC 6815](https://www.rfc-editor.org/rfc/rfc6815.txt)
- Y.1564: service configuration test (CIR stepped, typically 25/50/75/100%; EIR; overshoot above CIR/EIR to check policing) and service performance test (multiple services concurrently, 15 min / 2 h / 24 h); KPIs are information rate, frame transfer delay, frame delay variation, frame loss ratio, availability. — [Wikipedia: ITU-T Y.1564](https://en.wikipedia.org/wiki/ITU-T_Y.1564) (secondary; the ITU text itself was not retrieved)

### Inferences
- [INF] **Topology consequence.** Because loss = TX - RX on one router and latency is measured on packets the generator receives, a circuit test with traffic-generator must be a loop: site A sends with `ip-dst` = an address of its own (another port or the same one) and `ip-gateway` = the far-end router, which routes the packets back over the circuit. The far end can be any vendor's router (it only forwards), unlike btest. But every frame crosses the circuit twice, so a loss or latency number is round trip: it cannot say which direction lost the frames, and each direction carries the same load (a 1 Gbps symmetric circuit tops out at line rate each way, fine; an asymmetric circuit is limited by its slower direction). This is the opposite trade to the owner's btest finding that `lost-packets` counts only loss into the initiator.
- [INF] Two independent generators, one per site, each sending one-way, would give TX at A and RX at B with no shared loss counter; per-direction loss would then have to come from comparing counters by script (and generator RX counting on B of A's stream id is undocumented). Unverified; would need a bench trial.
- [INF] **RFC 2544 mapping.** Frame sizes: exact (packet-size 60/124/252/508/1020/1276/1514). Throughput: no built-in binary search, but `quick ... duration= pps=` or `start/stop` plus reading `stats stream` could drive one from a script. Latency: min/avg/max per stream plus a histogram is richer than RFC 2544's 20 tagged frames, but the stamping method and clock are undocumented, and on a looped circuit it is RTT including far-end forwarding. Frame loss: yes (per stream). Back-to-back: no burst mode is documented (only continuous rate, `packet-count` on quick) - probably approximable with `packet-count` at line rate, unverified.
- [INF] **Y.1564 mapping.** Up to 16 streams with different DSCP/VLAN-priority/sizes gives multi-service; CIR/EIR/overshoot steps would be scripted rate changes; KPIs IR/FLR/FTD/FDV available per stream; availability not computed. But the round-trip limitation remains, and Y.1564 KPIs are normally per direction.
- [INF] Being CPU-generated with the tool's own statistics collection, it inherits the owner's "overloaded generator produces false loss" problem; MikroTik's own guidance (dedicated generator routers, 2 CCR1036 to test one) implies the generator should be a separate, stronger box than the device at the circuit edge.
- [INF] The device-mode default (7.17+) is a real deployment obstacle for remote customer-edge routers: enabling traffic-gen needs someone to press a button or pull power on site.

### Gaps
- How traffic-generator stamps packets (special-footer layout, size, whether minimum packet-size is constrained by it) and how JITTER is defined: undocumented in all three official doc sources; only a forum config shows `special-footer=yes`.
- Whether `mbps` is metered on the L2 frame (without FCS), L3, or wire: not stated. The 64 B example (`mbps=120` giving ~250 kpps per stream) is consistent with L2-without-FCS or with-FCS, not IP; not resolvable from the docs.
- Whether stats are readable from a script (`/tool traffic-generator stats stream print as-value` or `get`) - not documented; needs a bench check.
- Max rates on RB4011 / ROS 7: no official figure found; the only official numbers are ROS 6 RB1100AHx2 / CCR1036 examples.
- No ROS 7 changelog entry found that changes traffic-generator measurement behaviour, other than pcapng inject (7.21) and device-mode gating (7.17). Changelogs were only searched, not read line by line.

## 2. /tool/bandwidth-test: documented semantics

### Takeaway
MikroTik's documentation does not define `lost-packets`, the `*-average` fields, or which layer `local-udp-tx-size` refers to - the owner's bench findings (IP-packet throttle, far-end-received payload-layer tx average, per-interval lost-packets counting only inbound loss) fill a gap the vendor never documented. The documented points are: far end must be MikroTik, UDP mode sends >=110% of what the far side reports received, test *through* a router not from it, and a CPU >90% warning exists since v6.44 - which is MikroTik's own version of the owner's INCONCLUSIVE rule.

### Cited Findings
- [DOC] Client parameters: address, direction (both/receive/transmit), duration, interval (20 ms-5 s, default 1 s), protocol (tcp/udp), local-udp-tx-size / remote-udp-tx-size (28..64000, "Local transmit packet size in bytes"), local-tx-speed / remote-tx-speed ("Transfer test maximum speed (bits per second)"), random-data, connection-count (1-255), user/password. Server: allocate-udp-ports-from (default 2000), authenticate, enabled, max-sessions (default 100). — [help.mikrotik.com Bandwidth Test](https://help.mikrotik.com/docs/spaces/ROS/pages/7962644/Bandwidth+Test); [manual.mikrotik.com Bandwidth Test](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/bandwidth-test/)
- [DOC] Output fields tx-current, rx-current, tx-10-second-average, rx-10-second-average, tx-total-average, rx-total-average, lost-packets, status are shown but not defined; the doc does not say whether udp-tx-size is UDP payload or IP packet. — [manual.mikrotik.com Bandwidth Test](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/bandwidth-test/)
- [DOC] "The UDP tester sends 110% or more packets than are currently reported as received on the other side of the link." — [manual.mikrotik.com Bandwidth Test](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/bandwidth-test/)
- [DOC] "If you want to test real throughput of a router, you should run bandwidth test through the tested router not from, or to itself. To do this you need at least 3 routers connected in a chain: the Bandwidth Server, the router being tested and the Bandwidth Client." — [manual.mikrotik.com Bandwidth Test](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/bandwidth-test/)
- [DOC] random-data: "the payload of the bandwidth test packets will have an incompressible random data stream so that links that use data compression will not distort the results"; it "is CPU intensive" and should be off on low-speed CPUs. — [manual.mikrotik.com Bandwidth Test](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/bandwidth-test/)
- [DOC] Both ends must be MikroTik (measures throughput "to another MikroTik router"); "Bandwidth Test uses all available bandwidth (by default) and may impact network usability"; single-core limitation existed prior to v6.44beta39. — [help.mikrotik.com Bandwidth Test](https://help.mikrotik.com/docs/spaces/ROS/pages/7962644/Bandwidth+Test)
- [DOC] MikroTik at MUM EU19: bandwidth-test "Until v6.44 was single threaded, now both UDP and TCP tests support multi-threading"; "In v6.44 we added warning message when CPU load exceeds 90% (CLI only), to inform that CPU is bottlenecking results, not the link". Also: "Traffic generation/elimination takes at least the same amount of CPU resources as simple traffic forwarding. The router needs to do both generate traffic and then forward it to destination." — [MUM EU19 "Understanding throughput"](https://mum.mikrotik.com/presentations/EU19/presentation_6767_1552293932.pdf)
- [DOC] Same slides on frame overhead: a 64 B L2 packet "actually consumes 102 bytes on the wire" ("64/102 = 62.45%"), and a 1500 B L2 packet "actually consumes 1538 bytes on the wire" ("97.53%"); the slide explains the overhead as the 7 B preamble + 1 B SFD and a 12 B interframe gap. (The 1500 B case is 38 B of overhead, which matches the repo's `size + 38` wire figure for an IP-packet size; the 64 B case as printed on the slide is also +38, so the slide's "64 byte Layer2 packet" is really counted like an L3 packet. Note the inconsistency rather than rely on it.) — [MUM EU19](https://mum.mikrotik.com/presentations/EU19/presentation_6767_1552293932.pdf)
- [DOC] Device-mode: bandwidth-test is disabled in home and basic device-modes, enabled in advanced and ROSE (factory device-mode from v7.17). — [help.mikrotik.com Device-mode](https://help.mikrotik.com/docs/spaces/ROS/pages/93749258/Device-mode)

**/tool speed-test (btest-based)**
- [DOC] Measures "ping, jitter, TCP and UDP throughput from one MikroTik device to another"; "based on the Ping Tool and Bandwidth Test"; runs five sequential tests (ping at 50 ms spacing, TCP receive, TCP send, UDP receive, UDP send); connection-count default 20 (or core count if more); default duration 54 s; outputs ping min/avg/max, jitter min/avg/max, loss %, TCP/UDP down/up, local and remote CPU. At 100% CPU on either side it warns "results can be limited by cpu, note that traffic generation/termination performance might not be representative of forwarding performance". Far end must run the btest server. — [manual.mikrotik.com Speed Test](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/speed-test/)
- [DOC] Introduced in v6.44, CLI only; "automatically determines optimal number of test streams based on the CPU core/thread count on both devices". — [MUM EU19](https://mum.mikrotik.com/presentations/EU19/presentation_6767_1552293932.pdf)

### Inferences
- [INF] The "110% of what the other side reports received" design explains the owner's finding that `tx-total-average` reflects what the far end received: btest's transmit logic is driven by far-end receive reports, so the reported "tx" number is feedback from the receiver. The doc says this only for unthrottled UDP; the bench showed it holds with a throttle too.
- [INF] The owner's `cpuLimit` of 90% matches MikroTik's own v6.44 CPU warning threshold - a citable vendor basis for the INCONCLUSIVE rule.
- [INF] speed-test adds latency/jitter/loss from ping but at fixed 50 ms ping spacing, not under load at a chosen frame size, and without verdicts; it is not a better acceptance tool than the owner's script.

### Gaps
- No official definition of lost-packets (per-interval vs cumulative, which direction), tx/rx averages, or the udp-tx-size layer. The owner's bench records are, as far as I can find, the only precise statement of these semantics.
- No official statement of btest accuracy or of how the btest protocol sequences packets.

## 4. Hardware: switch-chip traffic generation, loopback, MAC-swap reflector; MikroTik as reflector for a dedicated tester

### Takeaway
No documented hardware traffic generator, Ethernet loopback test mode, or MAC/IP-swap reflector exists on any MikroTik switch chip (CRS3xx/CRS5xx Marvell, CCR2116/2216 L3HW) in the official docs I found. A MikroTik can be the far end of a dedicated tester only by ordinary forwarding: routing the tester's traffic back (NAT or routes, CPU path) - which reflects IP but is not a wire-speed, loss-transparent MAC-swap loopback like EXFO/Viavi/Juniper/Cisco NIDs provide.

### Cited Findings
- [FORUM] "Loopback for RFC2544 testing" (Apr 2019 - Jul 2024): asked for RFC 2544 reflection, "swapping MAC and IP addresses, sending back the same data to the originator", at wire speed. Suggestions: paired dst-nat/src-nat rules to send traffic back, mirroring, containers; no confirmed working wire-speed reflector; a participant concluded "this feature is not existing". No MikroTik staff reply. — [forum t=147223](https://forum.mikrotik.com/viewtopic.php?t=147223)
- [DOC] For comparison, other vendors document RFC 2544 initiator/reflector/loopback modes with MAC swap on access devices (Juniper ACX, Cisco ME 1200). — [Juniper: Ethernet loopback for RFC 2544](https://www.juniper.net/documentation/us/en/software/junos/flow-monitoring/topics/concept/ethernet-loopback-overview-acx.html); [Cisco ME 1200 RFC 2544](https://www.cisco.com/c/en/us/td/docs/switches/metro/me1200/controller/guide/b_nid_controller_book/b_nid_controller_book_chapter_011011.html)
- [DOC] MikroTik's throughput talk says "all devices with a switch chip are capable of transferring data at wire-speed" but describes no test function in the switch chip. — [MUM EU19](https://mum.mikrotik.com/presentations/EU19/presentation_6767_1552293932.pdf)
- [DOC] The Traffic Generator doc describes the tool only as CPU packet generation on ports; nothing about switch-chip offload. — [help.mikrotik.com Traffic Generator](https://help.mikrotik.com/docs/spaces/ROS/pages/128221376/Traffic+Generator)

### Inferences
- [INF] A MikroTik as L3 reflector (dst-nat back to the source, or policy routes with the tester's own address as destination) goes through the CPU and conntrack, so at small frames it will add loss and latency of its own - the reflector becomes part of the measurement, which is exactly what RFC 2544 / Y.1564 loopbacks are designed to avoid.
- [INF] `loop-protect` on RouterOS Ethernet interfaces is a loop-detection feature, not a test loopback (not fetched in this session; flagged so the writer does not conflate them).

### Gaps
- Did not fetch the CRS3xx/CRS5xx switch-chip, L3HW or loop-protect pages to prove a negative; the conclusion rests on no MikroTik page, MUM talk or staff statement describing such a feature, plus the forum thread's null result.

## 5. MUM material and MikroTik's own published performance methodology

### Takeaway
MikroTik's published product test results are made with an external Xena RFC 2544 tester, not with RouterOS tools, using 30+ s trials at 64/512/1518 B with a 0.1% loss tolerance - which is not RFC 2544's zero-loss throughput definition but happens to equal the owner's 0.10% SLA. The only MUM content on these tools is MikroTik's EU19 throughput talk and community talks (EU16, EU17) on traffic-generator usage; none offers an RFC 2544 or Y.1564 procedure.

### Cited Findings
- [DOC] Product pages: "All tests are done with Xena Networks specialized test equipment (XenaBay), and done according to RFC2544 (Xena2544)"; "30+ second attempts with 0,1% packet loss tolerance in 64, 512, 1518 byte packet sizes"; configurations: bridging none (fast path) / 25 bridge filter rules; routing none (fast path) / 25 simple queues / 25 ip filter rules; "Test results show device maximum performance ... different configurations most likely will result in lower results". — [mikrotik.com hEX refresh](https://mikrotik.com/product/hex_2024); same methodology on e.g. [CCR2216-1G-12XS-2XQ](https://mikrotik.com/product/ccr2216_1g_12xs_2xq), [CRS326-24G-2S+RM](https://mikrotik.com/product/CRS326-24G-2SplusRM)
- [DOC] Historically (ROS 6) MikroTik published a wiki article showing "the necessary configuration and hardware to replicate the tests published in routerboard.com" using traffic-generator, noting fast-path inflates results and enabling conntrack brings them "close to the advertised PPS rate". — [wiki Performance Testing](https://wiki.mikrotik.com/wiki/Manual:Performance_Testing_with_Traffic_Generator)
- [STD] RFC 2544 throughput = highest rate with zero loss. — [RFC 2544](https://www.rfc-editor.org/rfc/rfc2544.txt)
- [DOC] MUM EU19 "Understanding throughput" (MikroTik): throughput definitions, L1 vs L2 wire speed (64 B = 62.45% L2 efficiency, 1500 B = 97.53%), fast-path/fasttrack, router-to-router testing costs, tool comparison (traffic-generator, btest, speed-test). — [MUM EU19](https://mum.mikrotik.com/presentations/EU19/presentation_6767_1552293932.pdf)
- [DOC/community speaker] MUM EU17 "MikroTik traffic generator study case" (José Manuel Román, FiberCLI): single-port, multi-port and QoS "fabricated packets" (DSCP-marked RTP/SIP) cases, wireless testing, pcap injection; lists uses as PPS, throughput, CPU, HW encryption on a DUT and latency/jitter/loss/bandwidth on a site-to-site link; notes TX/RX are unequal when the DUT does not send packets back. — [MUM EU17](https://mum.mikrotik.com/presentations/EU17/presentation_4081_1490963921.pdf)
- [DOC/community speaker] MUM EU16 "Securing and testing with Mikrotik" by the same speaker also covers testing (not read in full). — [MUM EU16](https://mum.mikrotik.com/presentations/EU16/presentation_3025_1456818897.pdf)

### Inferences
- [INF] MikroTik itself treats RouterOS tools as insufficient for its own RFC 2544 claims (it buys Xena), and its "RFC2544" figures use a 0.1% loss tolerance rather than zero loss. A script that reports "PASS at 0.10% loss" is therefore aligned with how MikroTik reports its own numbers, but neither is strictly RFC 2544 throughput.
- [INF] Overall feasibility verdicts for the report writer:
  - **bandwidth-test**: usable for a two-MikroTik acceptance test with the owner's corrections; semantics undocumented by vendor; one-end view of loss; no latency under load. Not RFC 2544 or Y.1564.
  - **traffic-generator**: the closest native fit (exact frame sizes, per-stream loss, latency, jitter, OOO, DSCP/VLAN multi-stream, any-vendor far end) but only as a round-trip loop test, CPU-bound, gated by device-mode on 7.17+ factory units, undocumented timestamp/jitter method, no built-in RFC 2544 search or Y.1564 steps. Worth a bench trial on the RB4011 pair before any adoption, per the repo's "trials decide" rule.
  - **speed-test**: convenience wrapper over btest + ping; not an acceptance tool.
  - **CFM/Y.1731/TWAMP/hardware reflector**: not available natively as of the sources found (latest dated evidence Oct 2025).

### Gaps
- MUM EU16 and other regional MUM decks (e.g. KH17) not read in full; I found no MUM deck that presents an RFC 2544 or Y.1564 procedure on RouterOS.
- Whether the Xena "0.1% loss tolerance" is per-trial loss ratio or something else is not explained on product pages.
